## 0.5.3

### Patch Changes

- [#774](https://github.com/Anastasia-Labs/lucid-evolution/pull/774) [`a1e17b8`](https://github.com/Anastasia-Labs/lucid-evolution/commit/a1e17b878940bdb1a2f80d68300ec5276d88c85f) Thanks [@colll78](https://github.com/colll78)! - Plutus Data constructors in the general form (CBOR tag 102, used for constructor indexes above 127) now decode as Plutus decodes them. The index and fields may be a definite list of exactly two elements or an indefinite list of two elements and a break; any other length is an error. Before, the list length was not checked and the break of the indefinite form was left unread, so a list, map or constructor holding such a constructor ended at that break. This applies to `apply_params_to_script` parameters and to datums and redeemers in the transactions given to `eval_phase_two_raw`; `eval_program_raw` arguments already decoded this way. The fix is in `pallas-primitives`, patched to `colll78/pallas` until a release includes it.

## 0.5.1

### Patch Changes

- [#770](https://github.com/Anastasia-Labs/lucid-evolution/pull/770) [`6b7264c`](https://github.com/Anastasia-Labs/lucid-evolution/commit/6b7264c5d78263e39a7c4df07ad095af5f43b9cc) Thanks [@colll78](https://github.com/colll78)! - The Node.js builds recover from a wasm trap. A trap or a stack overflow inside wasm used to leave the instance unable to run anything after it, so every later call threw `RuntimeError: memory access out of bounds`. Now, after a call throws, the next call first replaces the instance with a fresh one; the error itself is rethrown unchanged. A result returned before the replacement throws when read afterwards, and freeing it, explicitly or by garbage collection, does not touch the new instance. This applies to the Node.js entries of `@lucid-evolution/uplc`, `@lucid-evolution/uplc/speed` and `@lucid-evolution/uplc/size`. The browser, worker, workerd and edge-light builds are unchanged and do not recover: a bundler instantiates their wasm once, so after a trap the page or worker has to load the package again. The bindings are now generated by wasm-bindgen 0.2.126.

## 0.5.0

### Minor Changes

- [#768](https://github.com/Anastasia-Labs/lucid-evolution/pull/768) [`9bee0d5`](https://github.com/Anastasia-Labs/lucid-evolution/commit/9bee0d54036b8cb8a765c2ea3bb5c44b3a9ed4a2) Thanks [@colll78](https://github.com/colll78)! - Add `eval_builtin_raw`, which evaluates one builtin applied to constant arguments exactly as the pinned evaluator does for a Plutus V3 script at a given protocol version (9 to 12). Arguments and the result cross as flat-encoded constants, and BLS12-381 points (and lists and arrays of them) as their compressed bytes. The result says whether the builtin returned a value, how it failed (not available at that protocol version, arguments rejected before costing, or failed after costing), and the builtin's charge under Plutus' default Plutus V3 cost model, excluding the machine's per-step costs. `BuiltinValueKind` and `BuiltinErrorKind` name the codes of the argument and result kinds and of the error kind. `eval_program_raw` and `uplc_build_info` are unchanged.

### Patch Changes

- [#766](https://github.com/Anastasia-Labs/lucid-evolution/pull/766) [`863dc73`](https://github.com/Anastasia-Labs/lucid-evolution/commit/863dc73c66fa0297c1d6b3a15dfaa6d8f89f360d) Thanks [@colll78](https://github.com/colll78)! - `eval_program_raw` evaluates deeply nested `Data` arguments without exhausting the stack. Arguments are decoded straight into the evaluator's own `Data`, whose decoding, comparison, serialisation and release never recurse, instead of through pallas' recursive `PlutusData`, so an argument nested 100,000 levels deep evaluates like any other, in both the speed and size builds. Arguments are now decoded exactly as Plutus' `decodeData` decodes them. A byte string or big integer with a chunk of more than 64 bytes, a big integer tag outside the head of its own byte, or a tag 102 constructor that is not a pair of an index and fields is refused as an invalid argument, as it can never be Data on chain. A big integer in indefinite-length chunks and a tag 102 in a longer head, which pallas refused, are accepted. A tag 102 constructor in an indefinite-length array inside a list or map, which pallas closed one break too early and so decoded to different Data, now decodes to the Data Plutus decodes. Every other argument decodes to the same Data as before, with the same results and ex-units.

- [#767](https://github.com/Anastasia-Labs/lucid-evolution/pull/767) [`05bcd09`](https://github.com/Anastasia-Labs/lucid-evolution/commit/05bcd092ad9da63939a37eabc2bd7204ac85401c) Thanks [@colll78](https://github.com/colll78)! - `rotateByteString` now runs in time linear in the length of its argument for every rotation amount. Before, rotating by a small negative amount took time quadratic in the length: about 16 s for a 128 KiB byte string. Results, ex-units and errors are unchanged.

## 0.4.0

### Minor Changes

- [#759](https://github.com/Anastasia-Labs/lucid-evolution/pull/759) [`ae71a45`](https://github.com/Anastasia-Labs/lucid-evolution/commit/ae71a459717eef04d148648f49500523f927702a) Thanks [@colll78](https://github.com/colll78)! - Support protocol version 11 (van Rossem) in the Aiken evaluator: the Plutus V3 array builtins and constants, the new Value and BLS builtins, `case` on built-in types, and the builtins that become available to Plutus V1 and V2. Evaluation follows the Haskell evaluator, plutus-core 1.71: builtins unlift their arguments before they are costed, integers and bytestrings passed to builtins are bounded as on chain, and costing saturates like Plutus, and scripts are scope-checked as the ledger does: before protocol version 12 a free variable inside `constr` or `case` is admitted and only fails the program if it is evaluated, whatever its de Bruijn index. `Data` is handled as Plutus handles it: before protocol version 11 `constrData` takes any integer as the constructor index, `serialiseData` gives the canonical encoding whatever encoding the `Data` was decoded from, and `equalsData` compares negative big integers by value. Transactions are evaluated at protocol version 11 only when `eval_phase_two_raw` is given that version; omitting it keeps protocol version 10. Scripts are decoded as the ledger decodes them: a program's UPLC version must be available to its Plutus version at the protocol version, a constructor has at most 1024 fields, a constant's type is bounded in size, nothing may follow a flat program, and nothing may follow a Plutus V3 script's CBOR. As the ledger does, `eval_phase_two_raw` fails a Plutus V3 script that returns anything other than unit, and a builtin whose parameters are missing from the given cost models costs the maximum, so no budget affords it. `verifyEd25519Signature` returns false for public keys and signature points of small order and for public keys not encoded canonically, as libsodium does. Scripts nesting terms thousands of levels deep are decoded and evaluated without overflowing the stack.

  Add `eval_program_raw`, which evaluates a flat-encoded UPLC program applied to CBOR `Data` arguments outside of any transaction, at any protocol version from 5 to 12 (Dijkstra, where UPLC 1.2.0 programs can `case` on `Data`), and returns whether it succeeded, why not, its cost and its traces, and `uplc_build_info`, which describes the build: the uplc crate it was built from, each Plutus version's cost model length, and a self-test of its semantics.

### Patch Changes

- [#751](https://github.com/Anastasia-Labs/lucid-evolution/pull/751) [`d89f7e4`](https://github.com/Anastasia-Labs/lucid-evolution/commit/d89f7e4bb46bee3a3f782d39ba167b1622dfee62) Thanks [@colll78](https://github.com/colll78)! - Update the Aiken evaluator to unreleased Aiken `main` after 1.1.24, plus aiken-lang/aiken#1456. Evaluation is faster in five ways:

  - The CEK machine itself is faster.
  - Each transaction's script context is built, and its spent inputs are resolved, once per transaction instead of once per redeemer.
  - Recently decoded scripts are kept across calls in a bounded cache. It holds up to 64 scripts and 256 KiB of serialised scripts, about 64 MB at most once decoded.
  - `Data` values are shared between script contexts and builtins instead of copied.
  - Builtins with constant cost no longer measure the size of their arguments. Scripts that pass large `Data` values to builtins such as `chooseData`, `unConstrData` or `sndPair` evaluate much faster.

  On 108 real Midgard transactions, `eval_phase_two_raw` is about 2.3x faster than the previous unreleased build. Results and ex-units are unchanged.

  If an earlier call trapped while the script cache was in use, later calls skip the cache instead of failing.

  One error message changes: evaluating a Plutus V1 script without a V1 cost model now names `PlutusV1` instead of `PlutusV2`.

## 0.2.23

### Patch Changes

- [#728](https://github.com/Anastasia-Labs/lucid-evolution/pull/728) [`c25e239`](https://github.com/Anastasia-Labs/lucid-evolution/commit/c25e2395f77b9048c45a8013d5db8337e594135a) Thanks [@colll78](https://github.com/colll78)! - Fix unbounded wasm memory growth by dropping the `wee_alloc` global allocator

  `wee_alloc` has been unmaintained since 2019 and its free lists never return
  freed blocks to the allocator, so every `apply_params_to_script` and
  `eval_phase_two_raw` call grew wasm linear memory permanently. Because wasm
  linear memory can only grow, a long-lived process walked monotonically into the
  ~4 GiB wasm32 ceiling, at which point Rust's allocator aborts and the next
  evaluation surfaces to JavaScript as `EvaluatorError: unreachable` — a
  WebAssembly trap that reads like an on-chain validator rejection.

  Measured with `apply_params_to_script` over an 845-byte parameterized Plutus V3
  script, 2000 calls:

  |                      | growth per call       | after 2000 calls       | wall time |
  | -------------------- | --------------------- | ---------------------- | --------- |
  | `wee_alloc`          | 33,554 bytes          | 65.13 MiB and climbing | 502 ms    |
  | default (`dlmalloc`) | 0 bytes after warm-up | 1.25 MiB, flat         | 277 ms    |

  Removing the allocator costs 1,322 bytes of wasm (+0.14%) and makes the module
  45% faster, since `wee_alloc` traded speed for a size win that no longer exists.

### Patch Changes

- [#141](https://github.com/Anastasia-Labs/lucid-evolution/pull/141) [`eef3d42`](https://github.com/Anastasia-Labs/lucid-evolution/commit/eef3d421b4cdf12638169ece49e4c00fce6e3356) Thanks [@solidsnakedev](https://github.com/solidsnakedev)! - Transaction chaining is a feature that allows to chain multiple transactions in one block , the endpoint chain() allows to accomplish this by returning a tuple with three elements:

  1. **newWalletInputs**: This includes all UTXOs that were not spent in the transaction and the new wallet UTXOs derived from the output transaction.
  2. **derivedOutputs**: The derived outputs extracted from the completed transaction.
  3. **tx**: The new transaction that is ready to be submitted.

  ```
    const [newWalletInputs, derivedOutputs, tx] = await user
      .newTx()
      .pay.ToAddressWithData(
        contractAddress,
        {
          kind: "inline",
          value: datum,
        },
        { lovelace: 10_000_000n }
      )
      .chain();

      const signed = await tx.sign.withWallet().complete();
      const txHash = await signed.submit();
  ```

  To construct a new transaction using tx chaining, the UTXOs belonging to the wallet must be overridden. This is necessary because these UTXOs are not yet recorded on the blockchain.

  ```
  user.overrideUTxOs(newWalletInputs);
  ```

  This function updates the wallet's UTXOs to set the new ones, ensuring the next transaction chaining can be constructed correctly.
